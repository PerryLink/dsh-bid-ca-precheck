# Public World Bank benchmark — `dsh-bid-ca-precheck`

> **The bid side is synthetic.** The World Bank notices are requirements-side public data. The bidder
> name, responses, verdicts, evidence placeholders and injected defects are generated fixtures. They are
> **not** real bidder submissions and say nothing about any company's compliance, eligibility or outcome.

> **Not a legal or procurement conclusion.** The plugin's rule pack cites Chinese tendering-law provisions.
> This bench uses World Bank notices only as a public source of requirement text. The benchmark exercises
> the plugin's register checks; it does not apply Chinese law to a World Bank procurement and does not
> decide whether any bid is valid, responsive or should be rejected.

This directory is an end-to-end benchmark for the real `dsh-bid-ca-precheck` plugin. It downloads public
World Bank procurement notices, turns them into the bid-compliance register shape the plugin reads, injects
labelled register defects (plus four explicit blind-spot probes), and calls the **registered tool from
`../../lib/index.mjs`** with generated JSON. No check is reimplemented.

The headline result from the recorded snapshot is in [RESULTS.md](RESULTS.md). The machine-readable
version is [summary.json](summary.json).

---

## Quick start

From the repository root:

```sh
node bench/public-worldbank/fetch.mjs
node bench/public-worldbank/adapter.mjs
node bench/public-worldbank/evaluate.mjs
```

`fetch` writes the raw response and a metadata sidecar to `.data/`; `adapter` writes the requirements pack,
the generated cases and a benchmark-local rule overlay; `evaluate` registers the real tool, runs every case
in both modes, and rewrites `summary.json` and `RESULTS.md`.

Requirements: Node.js 22.19+ or 24+ (the repository's `engines` range), network access for `fetch`, and the
already-built `lib/index.mjs` plus the repository's installed dependencies.

| Path | Purpose |
|---|---|

| `RESULTS.md` | Human-readable report generated by `evaluate.mjs`. |

The `.data/` directory is deliberately ignored. The tracked report carries the raw SHA-256, the selected
notice identifiers and the overlay hash so a run can be audited without committing the public-data dump.

## The plugin contract this bench targets

The inspection covered `src/index.ts`, `src/model.ts`, `src/config.ts`, `src/view.ts`,
`rules/bid-ca-precheck.yaml`, `samples/quickstart/` and `tests/fixtures/`.

- The built entry point exports `name`, `inject`, `Config`, `apply`, `TOOL_NAME` and `resolvePackageFile`.
  `apply(ctx, config)` registers exactly one tool: `bid_ca_precheck`.
- The tool accepts `file` or `material` (inline JSON/YAML), an optional `rulesFile`, and an optional `only`
  list. `evaluate.mjs` uses `material` and, in configured mode, `rulesFile`.
- The material is a **bid compliance response register**:
  - top-level header aliases: `project`, `tenderNo`, `bidder` (and Chinese equivalents);
  - a row list under `rows`, `items`, `clauses` or `条款`;
  - row columns: `clause`, `requirement`, `response`, `verdict`, `evidence`, `note` (and Chinese/English
    aliases such as `条款号`, `招标要求`, `投标响应`, `响应结论`, `证明材料`).
- Unknown row fields are retained by the reader but not consumed by the shipped rules. This is why the
  adapter can mirror `notice_type` and `submission_deadline_date` into a row for the blind-spot probes.

The shipped rule pack has six rules:

| Rule | Severity | Column / header it reads | What it checks | Default behaviour |
|---|---|---|---|---|
| `BC-001` | warn | `response` | Each present requirement row has a recorded response | Executes |
| `BC-002` | info | `verdict` | The value is in the configured verdict vocabulary | **Skipped**: `values: []` ships empty |
| `BC-003` | warn | `clause` | Clause numbers are unique, ignoring whitespace | Executes |
| `BC-004` | warn | header `project`, `bidder` | The register declares its project and bidder | Executes |
| `BC-005` | warn | `requirement`, `evidence` | High-risk rows carry evidence | **Skipped**: `highRiskKeywords: []` ships empty |
| `BC-006` | warn | `requirement` | No unreplaced placeholder (`【】`, `{{}}`, `XXX`, `TBD`, …) | Executes |

The default mode uses this pack unchanged. The configured mode uses a generated overlay that fills **only**
`BC-002.values` with `["SYNTHETIC_ACK"]` and `BC-005.highRiskKeywords` with
`["Construction", "construction", "CONSTRUCTION"]`. Everything else is the shipped pack. The overlay is
written to `.data/rules-configured.yaml`, is versioned `2026.1-bench-configured`, and is not a release
artifact.

## How notices become cases

1. **Fetch** one page of the public API. No token, key or account is used.
2. **Filter** locally to notices that:
   - are `Invitation for Bids` (not contract awards, EOI or general procurement notices);
   - carry a parseable `submission_deadline_date`;
   - carry all six consumed fields (`bid_reference_no`, `notice_type`, `submission_deadline_date`,
     `project_ctry_name`, `bid_description`, `procurement_method_name`);
   - have a construction-related `bid_description` (`/construct/i`) and one of the configured high-risk
     keyword variants;
   - contain none of the BC-006 placeholder terms.
3. **Select** deterministically: sort by `project_ctry_name` then `bid_reference_no`; take one notice per
   `project_ctry_name` group in the first round, then fill from the remaining sorted candidates. The final
   selection is sorted the same way. In the recorded run: 200 API rows → 31 IFB → 18 candidates → 8
   selected, one per group: Cambodia, Cameroon, Chad, Eastern and Southern Africa, Ethiopia, Malawi,
   Philippines, Western and Central Africa.
4. **Requirements pack.** Each selected notice is projected to the six consumed fields plus `project_name`
   and `notice_id` when present. No field is invented. The pack is `.data/requirements.json`.
5. **Clean register.** One notice per clean case. The header carries the notice's `project_name` (or
   `project_ctry_name` fallback), `tenderNo`, and a clearly synthetic bidder
   (`SYNTHETIC-BIDDER-NOT-A-REAL-COMPANY`). The row mirrors the notice's clause, description and metadata;
   the bid-side cells are `SYNTHETIC_ACK` / `SYNTHETIC_EVIDENCE` placeholders. No real bidder is claimed.
6. **Mutations.** A single labelled defect is injected into a clean case and the expected issue count is
   recorded. The mutation cases cover all six rules, including a clause that differs only by an internal
   space and a header with both project and bidder missing (one BC-004 finding, not two).
7. **Blind-spot probes.** Four cases change something the nine-rule pack does not check: a row field it
   ignores (deadline, notice type) or the row set itself (extra or missing row). They expect zero issues
   and are excluded from P/R; they document the scope limit instead of pretending to test it.

| **Total** | **26** | 8 clean + 14 mutations + 4 blind spots |

### What the requested defects map to

- **Missing required response** → `bc001-missing-response-a/b`: the row is present, the `response` cell is
  blank. `BC-001` detects it.
- **Unmatched requirement**:
  - the closest detectable symptom is a requirement row whose response is blank (`BC-001`, above); the
    plugin can point at the missing response, not at the missing match;
  - a requirement that has no row at all, or a bid row whose clause is absent from the requirements pack,
    is undetectable. The plugin sees only the register it is given and has no referential-integrity rule,
    so both are blind-spot probes (`blind-missing-bid-row`, `blind-extra-bid-row`).
- **Wrong deadline / wrong notice type** → `blind-wrong-deadline` and `blind-wrong-notice-type`. The
  adapter changes the row's `submission_deadline_date` or `notice_type`; the reader retains the fields, but
  BC-007 checks bid vs notice deadline; BC-008 checks notice type vs material category; the blind wrong-notice-type probe does not carry the material category, so it remains a negative control.
  as blind spots, not as successful detections.

## Scoring

Every case carries an `expected` map of `ruleId × count`. The evaluator runs the real tool and counts
issues by `ruleId` from `result.reportJson`. For each scored rule and case:

```
TP += min(expected, actual)
FP += max(0, actual - expected)
FN += max(0, expected - actual)
precision = TP / (TP + FP)
recall    = TP / (TP + FN)
```

- Clean cases expect zero issues from every scored rule.
- Mutation cases expect exactly one issue of the target rule and zero from the others.
- Blind-spot probes expect zero issues and are excluded from P/R; they are listed separately.
- A case is **case-exact** when every scored rule's actual count equals its expected count.
- In default mode, `BC-002` and `BC-005` are **not scored** because they are skipped by design. The two
  mutation cases that target them are marked "not scored (rule skipped)" rather than counted as false
  negatives. In configured mode all six rules are scored.

The counts are counts of issues, not counts of rows. A case with two rows and one defective row expects one
issue, not one issue per row.

## Limitations

- **Synthetic bid side.** No real bidder, bid submission, evidence document or outcome is claimed. The
  benchmark measures mechanical detection of injected register defects, not bidder performance.
- **Domain mismatch.** The plugin is a Chinese tender compliance-register checker. World Bank notices are
  used as public requirement text; the plugin's clauses are Chinese tendering-law provisions, not World
  Bank procurement rules. No legal conclusion about a World Bank procurement is drawn.
- **Register-internal only.** The plugin checks the register's completeness and consistency. It does not
  judge whether a response satisfies a requirement, whether evidence is authentic or sufficient, or whether
  a bid is valid, responsive or should be rejected.
- **Blind spots.** BC-007 checks a wrong submission deadline against the notice deadline; there is still no shipped rule for a wrong notice type, an extra
  bid row absent from the requirements pack, or a requirement with no bid row. The four probes show zero
  issues; that is the limitation, not a pass.
- **Generic engine vs. shipped pack.** `src/shared/rows.ts` implements date and field-comparison check
  kinds, so a deployment could add a deadline rule to its own rule pack. This bench deliberately does not:
  P/R is measured against the shipped nine-rule pack, and a benchmark-authored rule would score that rule,
  not the plugin's shipped behaviour. Detecting missing or extra rows against an external requirements
  pack would need a new check kind or code, which this bench does not add.
- **Two rules off by default.** `BC-002` and `BC-005` depend on institution/project lists that ship empty.
  The configured overlay is a benchmark-local deployment, not the default plugin behaviour.
- **Live API.** The selection is deterministic for one fetched page, but the notice set changes over time.
  The recorded results are tied to the recorded retrieval timestamp and raw SHA-256. Re-running
  `fetch → adapter → evaluate` refreshes the sample and may change the case IDs and numbers.
- **Broad search.** `qterm=construction` is a full-text search, not a procurement-method filter. The page
  includes contract awards and other types; the local filter removes them. The API total (128,545) is not a
  count of construction IFBs.
- **No real documents.** There is no PDF/OCR path, no tender document, no evaluation method, no bid
  document. The material is generated JSON only.
- **Case labels are injected.** P/R describes how faithfully the tool reproduces these labels, not how well
  it would score a real procurement.
- **License nuances.** The dataset-level license is CC BY 4.0; the API payload itself has no license field
  and general site terms also apply. Individual notice text may contain third-party content. Re-verify
  before redistribution; this is not legal advice.
- **Snapshot, not a benchmark service.** There is no CI job, no fixed corpus and no leaderboard. The output
  is a reproducible local run over a live public API.
